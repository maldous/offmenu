METHOD / READ WITH THE RESULTS
What this experiment actually measures.
The methodology below describes the four-strategy fixed-slice benchmark. The real RPC panel uses its editable fetched window, one sample per HTTP/client-reuse/RPC arm, and the exact query/cost/runtime recorded in its export. The paired panel compares five approaches over three rotated orders and three samples per approach/state, with qualified compact-input decode costs in its own export. All experiments retain snapshot and source qualifiers; none is a global search or cloud-load benchmark.
Inspecting this browser’s capabilities…
Same rows, same query output
Each collection is a fixed first25-row page. Ordered source IDs and snapshot must match; every approach’s query result is compared with the HTTP baseline’s JSON. Profiles/metrics use Fineli; ingredients are occurrences; recipes are body references. This is a combined projection/transport experiment, not an isolated compression benchmark.
One observation per phase
Each click runs one first-load and one repeat sample per approach, in fixed HTTP → compact → bundle → prefetch order. Prefetch preparation is a separate measured row. No medians, percentiles, randomized order or confidence interval are implied. Run again on a real Android phone before choosing an architecture.
Timing boundaries
Query end to end excludes shared page/script/manifest startup. Fetch + body includes wait for response and ArrayBuffer read; decode/parse includes UTF-8, envelope/base64/inflate where applicable, then JSON parsing. Index/query are timed; data-ready stops before DOM/frame scheduling. A frame callback is not a paint measurement. No INP/LCP or main-thread long-task telemetry is implemented.
Known cache state only
First client load clears only this tab’s demo memory, not server/DNS/socket caches. Warm client rows reuse parsed data; HTTP repeats always fetch, with host cache state unknown. Prefetch here is explicit fetch into tab memory, not a rel=prefetch browser hint. Both its request and prepaid bytes are counted. Scope changes clear memory/results; actual personal-profile auth is outside this demo.

Download, processing and DOM readiness
Data-ready covers fetch/body read, decoding, JSON parsing and query work. DOM-ready adds result serialization, text insertion and synchronous bounding-box layout. Server stages sit inside network time and must not be added again. Shared page/module bootstrap is excluded from every arm.

Qualified compact input and gzip
The new pair uses all25 original source rows with source scope/pagination and every original row field retained except unrequested values. Protein, alcohol and basis keep their complete observation objects, including HOLD, units, method and definition. The same unchanged query engine checks equivalent ordered output, scope and pagination against live full HTTP. This supports only these two fixed queries, not omitted nutrients or global search. Fetch, envelope parsing, base64 decoding, inflate, final JSON parsing and query costs are measured. It is application-level compression, not an HTTP Content-Encoding benchmark; full encoded network bytes remain unknown where timing entries are unavailable. Warm parsed reuse makes no request. Static read-model generation is prepaid build work, not removed from the architecture.

05 / BOUNDARIES THAT CHANGE THE RESULT
Fresh data. Separate profiles.
Pinned public snapshot
Frozen client slices and HTTP pages use the same snapshot ID. A server snapshot conflict fails the comparison instead of silently mixing versions. Source observation dates are not today’s prices or current recommendations.
Private profile isolation
The profile workload reads public Fineli source profiles. Scope A/B is synthetic: switching scopes clears this demo’s parsed cache and visible results. No actual private profile is fetched, uploaded, persisted or placed in shared caches. This demonstrates client separation; backend authorization is not tested.
