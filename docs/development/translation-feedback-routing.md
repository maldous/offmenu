# Translation feedback: source-to-tracker contract

The [public form and maintainer guide](../translation-feedback.md) explain what a contributor can submit. The [receiving adapter](../../tools/delivery/translation_feedback.py) routes a reviewed **reference**, not a copy of that public content. Its input is an issue number. It is not an installed application, network service, webhook, tracker credential, scheduler, release step or new work queue.

## Boundaries for a real consumer

The authorized intake owner supplies the following ports to `receive(number, route, ports)`. No default implementation performs network calls or writes. Real bindings belong in the existing private operating environment. Do not invoke a create port against a production tracker until its writer and operation recovery contracts are qualified.

1. **Read the canonical source.** Resolve the number with the authenticated GitHub reader against the registered public repository, not a URL supplied by an event. Independently confirm that current repository visibility is public. Read the immutable repository and issue IDs, actual kind (exclude PRs), open state and canonical issue URL. Compute a digest of the exact reviewed revision using a single pinned serialization shared by the GitHub reader and moderation surface. That digest must cover title, body, visibility and any other facts used for approval. The title prefix is not proof of origin or categorization.
2. **Moderate before transfer.** A separately trusted reviewer produces an approval for that exact source ID and revision, indicating that the item is a translation suggestion and that even linking its public page is safe. Unsafe, private, security-related, unapproved or edited submissions stop. Do not infer approval from a checkbox, a username or instructions in a public issue. Public content can change after receipt. Later suspected abuse or disclosure goes to the existing moderation owner, not automatic re-posting or deletion.
3. **Bind the destination privately.** `route_current` verifies native UUIDs for the existing UIF team, its OffMenu project, its Backlog state and the tracking assignee designated in the owning record. It must verify the relationships and permitted identities, not resolve by display name or accept caller-provided UUIDs as authority. A tracking assignment is not an execution claim. No contact, contributor name, public title/body, screenshot, credential or private tracker link is copied back to GitHub. The Linear create payload contains only the generic title, canonical public URL, stable numeric source key and destination fields.
4. **Look up existing effects.** Use the exact source key containing the repository ID and the GitHub issue ID (not merely its number). The native destination reader must reconcile the private original-operation ledger and any existing records, including archived or reclassified ones, before reporting the lookup complete. A partial text search, one page, a filtered active view or an empty API response is not complete proof of absence. Conflicting provenance, multiple destinations, wrong scope or uncertainty requires reconciliation by the original owner. An already received issue can change workflow state without warranting a duplicate.
5. **Fence and reserve once.** The existing private authority serializes intake for this source key across all workers and persists the original effect intent before returning `Reservation.NEW`. It rechecks sole-writer authority, destination, source revision and moderation at the actual `create_reserved` boundary. Only the holder of that exact reservation may submit once. A reservation must survive restarts and may not expire into a new write after a timeout. If exclusive, durable reservation or the check at the effect boundary is unavailable, decline the operation. Do not substitute a local in-memory flag, a new persistent controller, a search-then-create race or generic Issue Sync.
6. **Read back and settle.** Verify returned native ID, exact team/project/assignee, initial Backlog state, source key and URL from the actual native issue. Settle the original intent with its native ID. Repeated observations of an existing match require a second read by ID and `reconcile_existing` to return the trusted **original native creation readback**: same native ID, source key and URL, team, project, assignee and initial Backlog state. A reservation, bare record ID, Boolean or observation of the current state is insufficient; never adopt an issue merely because someone copied a marker into it. If a write or readback is uncertain, report the stable key and reconcile the original intent, received record and authority; never retry under a new ID. No update to existing issues or outbound public comment is part of this adapter.

The [offline tests](../../tests/delivery/test_translation_feedback_routing.py) use synthetic ports. They exercise success, repeats, wrong/unsafe inputs, stale moderation, duplicate/conflicting matches, lost replies, effects that disappear from a search, and changed permissions/receipts. Passing them proves the contract under those assumptions only. It does **not** qualify a live writer, authenticated reader, publisher, accessibility, signed-in chooser or actual end-to-end receiving. A live verification needs an authorized safe original submission and a repeat observation of that **same** source, never two test submissions.
