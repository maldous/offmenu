# Agent capability selection and verification

OffMenu remains independently buildable. Agent skills, connected services and
UIF execution policy are optional development capabilities, not application
runtime dependencies or new release gates. Read current `AGENTS.md`, applicable
component instructions and the selected task before choosing a capability.
The approved product brief, source rights, existing owner and sole publisher
remain authoritative.

## Evidence to retain

For each selected cloud, Foo or CI environment, record the repository commit and
tree, executor and checkout owner, task/issue, exact capability source/version or
hash, invocation route, required authentication and operation scope, target
project/account, actual nonmutating check and remaining limitation in the
existing issue/handoff. Keep private receipts outside Git.

A readable skill is not automatic skill discovery. A catalog entry is not a
working engine. MCP authentication is not CLI authentication. A source/build
pass is not production acceptance. Verify each environment separately rather
than copying another host's availability claims. Reuse existing exact-input
qualification; a documentation change does not require replaying product suites.

## Safe reconstruction

Verify fresh accepted `develop` against the remote. Preserve dirty, held and
runtime-dependent checkouts; use a distinct isolated destination. Read scripts
before executing them; installation and build commands have their declared side
effects. Use writable environment-owned package caches
instead of changing home-directory permissions or global configuration.

Apply only the smallest selected check. Record executable/tool versions, source
and output hashes and actual terminal result. Do not turn missing optional
capabilities into blanket blockers for independent work, promote historical
evidence to current readiness, or claim a repository commit installs tools on Foo
or another cloud environment.

## Foo snapshot checks

When the deployed `u/admin/project_checks` schema in workspace `foo` offers
`source_branch`, select this project's exact feature branch and immutable
`expected_commit`. Read `catalog` first, resolve the branch with `discover`, then
run only the affected supported target under a new immutable `operation_id`.
Supply the bare branch name, not a `refs/heads/` prefix: the current helper
constructs that prefix itself. Reconcile with `status` for that same project and operation after uncertainty;
inspect both the original transport receipt and the inner target result.

The verified OffMenu catalog distinguishes `layout`, `delivery_check`, `build`,
web `test`, combined `check`, `release_plan`, `environment`, `delivery_tests` and
offline `provider_contracts`. There is no declared lint or deploy target. Select
only the necessary target, preserve accepted tests and original receipts, and
use `install_locked` only when its source-reviewed setup is required. A catalog
entry or transport success is not a passing check; only the exact target's
terminal result establishes its stated coverage. Revalidate schema and engine
identity before use because this is an environment capability, not a bundled
OffMenu dependency.

The standalone-product edition has no `offmenu.delivery` package or
`tests/delivery` suite. A helper catalog still advertising those historical
targets does not make them valid for this edition. Select compatible product
commands such as build or layout, and reconcile any stale profile through its
existing environment owner rather than restoring orchestration as a dependency.
