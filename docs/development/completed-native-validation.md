# Completed native coding to focused validation

A completed coding unit continues through its **original runtime** and the existing
native v1 `validation-bindings.json` and operation Journal. It does not publish a
same-issue successor, replace a successful catalog entry, create a staged coding
admission, or replay the original attempt. The original manifest, control base and
branch, request, native receipt, lease and output hashes retain their identities.

For `enrichment-resilience-focused` only, the owner-selected v1 validation binding
may add `candidate_root` to the existing six selection fields. The fixed profile
and bounded `stage.bind` producer are separate reviewed source. The committed
contribution has its actual candidate head and branch; these never relabel the
original executed workspace. The candidate must be a canonical, clean Git root,
have exactly the original native base as its sole parent, and change exactly the
native output files without derivation. Its working and committed bytes must
equal the original native receipt and retained workspace. The ordinary v1 binding
checks and binding identity include the entire selected value and file hash.

The adapter requalifies original native evidence independently: immutable entry,
admission, manifest, request, dispatch and intent binding; successful stopped
receipt and session; original source identity and scope; exact outputs; and the
original Pool row with matching binding/fingerprint, `finished/succeeded`.
Pool reads use SQLite read-only mode and never construct or admit a Pool lease.
The original workspace must still have its original head/branch and exact output
delta. Missing, active, cancelled, uncertain, changed or contradictory evidence
holds the transition.

An installed protected control checkout may advance for the reviewed profile
code while the completed native unit retains its old control base. This exception
is restricted to review/validation context, the same protected source path and
custody, the same original branch, an accepted guarded head descended from the
original base, and all original finished-native evidence above. Ordinary coding
and unstarted/active units retain exact head/base checks. The exception grants no
new coding execution and does not change the candidate source identity.

Independent unit review compares a contribution branch only after the full
native v1 contribution qualifier succeeds. Otherwise the existing manifest-branch
rule remains. The unit binding stays the original native binding; the existing
accepted contribution review and dated supplement remain evidence for that exact
source and output, not a new verdict about a control-code commit.

Root must provision and qualify the actual remote candidate at its exact head and
branch, prepare the original runtime's binding through the accepted fixed producer,
and coherently adopt reviewed profile/adapter source. The normal coordinator then
continues the one Journal operation and ordinary unit consumer. Local source and
preparation checks are not actual job, review-consumption, integration or product
acceptance evidence. This route changes no source permission or production/CIX hold.

When the fixed enrichment validator fails and its corrected executor is prepared,
the existing producer retains the previous selection in `history`. The adapter
accepts that history only for this focused native profile, with the same native
receipt, candidate root/source/branch, outputs and acceptance. Every retained key
must identify a canonical original Journal spec; only its executor hash may differ
from the current spec. Its status must be failed, with no accepted outputs,
cancellation or reconciliation requirement, and with the original deterministic
backend identities. A genuine regular original public failed receipt must exist at
`validation-receipt-<original-operation-key>.json` in the original runtime. Its full
canonical body must match the original Journal digest and prove a stopped read-only
failure bound to the original job, runner and policy. The global
`validation-receipt.json` remains available for final successful evidence.

The historical command is never executed or regenerated with the corrected
wrapper. Its original command/request hashes remain in the exact retained receipt;
the complete backend receipt may remain separate when its public projection omits
resource metadata. A sticky observation-intent flag or old incomplete-result
diagnosis does not negate a fully qualified closed failed terminal boundary.
Unknown/active history, missing or contradictory receipts, changed native identity
and output acceptance remain holds. No failed result is promoted to success.

The normal consumer can move its failed validation cache to the current prepared
selection only when the prior identity exactly matches a qualified producer
predecessor. That identity is derived from the retained selection/spec/native unit
and the existing checkpoint serialization of its history prefix; this is metadata
identity comparison, not reconstruction of a receipt. Approved/handled units,
unknown or unrelated cache identities cannot use this path. Existing history,
Journal rows, receipts and reserved job IDs remain untouched; the normal Journal
alone continues the already-prepared current operation.
