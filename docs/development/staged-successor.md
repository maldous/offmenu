# Staged successors in the current coordinator

A staged successor uses the existing owner-bound task packet, manifest,
`stage_binding` and reviewed-source v3 admission. The manifest must have empty
`allowed_paths`, exact stage/input paths, owner/resources/acceptance and genuine
`stage_origin` proof. Its stage binding and every immutable input pin must match
the owner configuration and task packet. No coding admission is created.

The coordinator qualifies the incoming stage, native publication context and
exact next catalog grant before archiving the previous request. The normal
native consumer must still lend its immediate unit-bound permit. A saved verified
projection, new handoff pointer or copied approval cannot supply that permit.
Publication uses the same fixed native CLI, custody and no-replay rules.

A wait or refusal records `successor_hold`. Exact fresh owner-qualified intake
remains qualified while waiting only for the native readback permit; other
refusals still hold intake. The actual permit rechecks the same authority.
Known original published/duplicate
custody retains its terminal publication status; pending, unpublished or uncertain
requests retain refusal behavior. This never upgrades an old held request.
Root alone may reconcile the actual old held cache from its exact original
publication custody/journal/catalog evidence, paired with a fresh qualified stage
and exact next catalog edge. The normal consumer then archives it once.

Native publication also requires the actual protected source to have its accepted
head on an allowed named branch, with the fixed native base as ancestor. Root
must include that immutable Git branch/ref in coherent adoption. Native pins use
only the existing required `MODULES` Python subset, each equal to the full sealed
source map. The control source head and the reviewed candidate contribution head
remain distinct identities. Source acceptance does not activate either route.

A frozen stage wrapper can retain an older control base when the same protected
control checkout advances. `context()` first verifies the current sealed source
and custody. The stage-only compatibility check then requires the identical
protected source path, unchanged wrapper branch, the currently guarded head and
the wrapper base as its ancestor, and requalifies the original stage origin.
Reviewed-source recovery keeps its existing limited observation mode; normal
review requires full original admission, provenance and candidate qualification.
The frozen wrapper, source path and inputs remain unchanged. Ordinary coding
still requires its exact wrapper head and branch.

The normal validation tick can qualify an already-admitted independent typed
review for a `validation` stage with `reviewed-source-v1` origin. It rechecks the
original admission, every frozen input, contribution provenance, candidate
identity and outputs, and the original terminal Journal receipt. It writes one
immutable `retained-typed-review-v1` incoming packet through the existing unit
writer; the normal unit consumer recomputes the entire packet before approval.
This separate evidence origin retains the typed review's actual fields without
inventing model, provider, reviewer thread or turn observations. The existing
standalone review and provenance supplement contract is unchanged.

For future operations, the Journal retains the actual public receipt body from
normal successful backend observation at the original reviewed runtime's fixed
`validation-receipt.json`. For an already-completed operation, the owner may
retain the original body there without changing frozen inputs or creating a new
operation. Its full content must match the original Journal digest, stopped
success, job, command, runner, policy, acceptance and output bindings, including
when the original executor predates the current source. A digest or status alone
cannot supply a missing body. Missing, changed or conflicting evidence holds the
unit; receipt custody failure preserves the terminal job and never reruns it.
The observed public projection is distinct from the complete backend receipt
(which can include resource details omitted by the existing dispatcher). Retain
the complete backend bytes separately as `validation-backend-receipt.json` when
collecting historical evidence; its digest need not equal the Journal's public
receipt digest. Never rebuild the public receipt from a status summary.

Unit approval keeps `accepted_delivery=false` and has no merge action. Existing
owner-native publication, outcome and refill phases still require their own
admitted evidence. This continuation starts no reviewer, model or coding work.

An owner-selected native integration boundary may pin exactly `reviewed_runtime`
(a canonical private directory) and `unit_review` (the existing file reference),
with the existing optional `publisher_invocation`. This finite context is not
accepted for release or Linear; legacy Engine contexts and empty Linear context
retain their existing rules. The trusted adapter wrapper preserves an admitted
`integration_acceptance` callback supplied by installed factory code. Context
JSON cannot select callbacks, and selection/unit/source/owner checks still apply.
