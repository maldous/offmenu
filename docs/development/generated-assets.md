# Checking the generated extension bundle

`extension/popup.js` is tracked generated code. Its source entry point is
`extension/popup-source.js`. The application build and the check below share
`scripts/extension-build-options.mjs`, preserving the existing bundle options.

After installing the repository's locked dependencies with the existing approved
install-script policy, run this **before** `npm run build`:

```sh
npm run check:generated
```

The command bundles the extension in memory with the installed esbuild and
compares exact bytes against `extension/popup.js`. It does not regenerate files,
approve package install scripts, install dependencies, collect data, or deploy.
The JSON output includes Node and esbuild versions, byte lengths, and SHA-256
hashes for the committed and generated bytes. A missing committed file is also
reported without creating it. Compilation or filesystem failures are errors,
not a successful drift assessment.

- Exit 0: the tracked extension bundle matches the current source and toolchain.
- Exit 1: the tracked bundle is missing or differs from the in-memory build.
- Exit 2: the check could not finish, for example because an input is invalid.

If regeneration is in scope, use `npm run build`, review the generated diff, and
rerun `npm run check:generated`. Running the build first can hide pre-existing
drift by overwriting the tracked bundle. An exit-1 report during a source or UI
hold is evidence to retain; it does not authorize changing the held artifact.

The focused tests are part of `npm test` and can be run independently:

```sh
node --test tests-web/generated-extension.test.mjs
```

This is an optional local check, not a new required CI gate. It covers the tracked
extension bundle only. Ignored build outputs such as `dist/`,
`cloud/generated.mjs`, and `netlify-return/i18n.js` are outside this check. A pass
does not establish full-build reproducibility, browser behavior, deployment
readiness, or dataset acceptance.
