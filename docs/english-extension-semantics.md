This is the Worker19 r3 correction of candidate44822a80 after independent Worker56 review9665 (manifest0dfda1ec), preserving proposal37176706 and its earlier review9525. ## API and existing execution boundary

`validate_extension(extension, policy, resolver)` returns a tuple of fixed diagnostic codes. It is pure with respect to caller documents: it neither changes them nor opens paths, writes files, fetches data, allocates IDs or emits graph records. `semantic_validator(policy,resolver)` adapts it to the existing reviewed `SourceContract.semantic_validator(row)` callback using the native sourceAssertion wrapper's data field. Existing `qualify` remains responsible for exact input inventory/bytes, independent count/IDs, schema checks, record provenance, resource limits and pre/post byte checks. No production factory, registry binding or accept invocation is installed.

The schema is closed and uses only local references; its canonical fingerprint is pinned in policy. The extension/evidence bound is8MiB by default, matching the existing record bound. Output diagnostics never contain source values or resolver exception text. Structural validity is separate from source-specific semantics and from acceptance. Activation remains not-authorized-by-artifact; goldAdmission remains not-admitted. New operations/purpose flags cannot appear in a sidecar to grant themselves access.

Resolver methods are trusted reviewed application interfaces over already selected evidence, not untrusted dynamic providers. `evidence(pin)` supplies selected bytes; every use checks the exact SHA and bound. `page` supplies qualified native page text. `grant` returns a typed Grant containing an actual SourceContract plus explicitly reviewed purposes. The callback requires the existing retain/parse/transform operation set, no holds, exact source/release and the exact input-contract fingerprint. Normalization and translation remain separate purposes of transform. A source JSON object, public URL, rights-file hash or invented pin cannot construct a Grant. All resolver witnesses must be included in the eventual reviewed factory's independently pinned input/context inventory. This candidate does not install that real-input factory.

## Exact record and native-location checks (F2)

The selected parsed file path/SHA/bytes and JSON or JSONL format/line/pointer/record ID are policy-bound. JSONL is split on literal LF bytes, not Unicode separators. Strict JSON rejects duplicate keys/nonfinite values. JSON Pointer decoding rejects invalid tilde escapes, append indices, leading-zero array indices and unresolved paths. Parsed source/release/record/original hash must match the selected input and actual native citation. Unknown upstream values are not replaced with guessed releases.

Targets resolve to their exact native extraction nodes. Whole-node evidence uses that node's inherited location. A narrower string field requires a separate qualified subfield locator with its own pin, exact record/pointer and native location; it cannot silently inherit a whole-line location as word evidence. Page/hash/span/range/line and UTF8 boundaries are checked against the existing native text. English output is never an offset source. Original native text and unknowns remain unchanged.

Assertion IDs are unique across assertion sections; conflict IDs have a separate unique namespace. Ambiguity, variant, competing assertion and external record references must resolve. Resolved conflicts require a typed ReviewedWitness from the trusted resolver, a selected review authority and an affirmative reviewed resolution. Its exact pinned scope binds conflict ID/content (excluding its own decisionPin), full native input binding and each competing assertion ID plus canonical SHA-256. Rejected, unresolved, stale-version and unrelated decisions cannot support a resolved state. An unresolved conflict with no decision remains visible. No original/superseded claim is removed.

Quantity witnesses are reviewed resolver mappings, not a new conversion engine. Their exact pin binds native record/original/target, source qualifier, normalized value/unit/basis, comparison/bound, conversion kind and factor/basis pins. Changing a factor, qualifier, unit or target invalidates the mapping. Literal-zero claims additionally agree with the native value lexeme and normalized zero. Unknown quantities stay unresolved; no trace/ND/blank-to-zero inference. Actual conversion definitions, density/food form, yields, nutrient retention, serving and wet/dry/edible bases remain source-policy responsibilities. This callback supplies no guessed values or factors.

## Qualified identity-role and source mappings (F1)

Opaque IDs are preserved as lexical source claim IDs; they are never cast to graph IRIs. `claim` returns a ResolvedClaim containing its own SourceContract, existing qualification result, exact candidate artifact and record locator. The callback verifies the result fingerprint, contract fingerprint/source/release/scope/candidate hash, exact source record ID/provenance, role and independently resolved graph IRI. Fixture qualification cannot satisfy a nonfixture caller. External product claims deliberately use their own qualified source/release; recipe provenance is not inherited.

The bounded product role is source-product-assignment, a resolver role label, NOT a new canonical graph class. It resolves to existing FoodProduct plus a source-scoped formulation/item snapshot represented by SourceRecord, Package and Market as applicable, and explicit bounded effective-period evidence. Package/market N/A requires reviewed evidence and a null resource; unknown is held. This slice supports explicit ISO-date closed validity intervals only; missing/open/unsupported temporal semantics stay unresolved for a separately reviewed mapping. Ingredient role resolves to qualified identity plus explicit material state, part and preparation. Missing form/snapshot/package/market/time or wrong role cannot support reviewed inheritance. No formulation/trade-item canonical type is invented.

### R3: reviewed relationships require their own witnesses

Null ingredient identity is allowed only with unresolved state and relation. Exact/broader/narrower relations require an identity reference; reviewed identity cannot retain unresolved relation. Proposed and rejected assertions are preserved without promotion. An unresolved assertion can retain a candidate reference with unresolved relation, but it cannot claim reviewed equivalence.

Endpoint qualification alone cannot establish either a native-to-identity mapping or product composition. A reviewed assertion calls `relationship(assertionId)` and requires a typed `ReviewedWitness` from trusted application code. Its authority must be explicitly selected in `EnglishPolicy.review_authorities` (empty by default), with exact authority also present in pinned scope. Review status must be reviewed and decision state affirmed. A source sidecar cannot configure this authority set or construct a resolver witness from its own evidence pins.

The witness binds its exact type (native-ingredient-identity or product-ingredient-relationship), assertion ID and canonical SHA-256, relation, full native input binding (including source/release/record, original and parsed hashes, parser/transform, format and locator), ingredient claim/version/qualification and food form. Native mapping additionally binds the exact target. Product composition additionally binds the product claim/version/qualification and all food-product/formulation/item snapshot, package, market and effective-period fields. A generic policy, valid unrelated endpoint, translated name or endpoint existence is insufficient. Witness inputs must be included in the eventual independently pinned application factory inventory; no factory is installed here.

These are bounded resolver decision types, not new graph classes or predicates. Assertion hashes include assertion evidence but not the separately resolved witness pin, preventing circular hash references. Conflict hashes exclude only their own decisionPin for the same reason; competing assertion versions are fully hashed.

`productIngredientLinks` remains a source assertion on that exact qualified assignment/snapshot. It does not establish culinary usability, equivalence, allergens or dietary suitability. A parent FoodProduct alone cannot establish formulation-specific composition or nutrient/dietary inheritance.

Unresolved assertions remain unpromoted; unknown is never a fabricated negative. ### PR63: bounded evidence work and packaged canonical schema

Each validation creates a fresh evidence snapshot cache keyed by exact
`(path, sha256)`. Only bytes that pass the pin, per-blob size and hash checks enter
that cache. Repeated references return those immutable verified bytes without
another resolver call or hash. Different hashes at the same path remain distinct;
a new validation always resolves/verifies again. No cache survives the call or
changes source rights, provenance or reviewed-relationship semantics.

Trusted EnglishPolicy additionally limits cumulative unique evidence to32MiB
(`max_total_evidence_bytes`) and resolver dispatches to1024
(`max_evidence_reads`) by default. Both must be positive integers. The call limit
is checked before dispatch. Returned byte size is checked against the remaining
cumulative budget before hashing/caching, failing with the fixed
`english-evidence-work-bound-exceeded` diagnostic. A rejected final return can
retrieve at most one additional per-blob-sized value; it is not hashed or cached.
As before, the trusted resolver must itself honor its selected-byte/per-call
resource contract: this pure callback cannot prevent allocations or hidden work
inside arbitrary resolver code and is not an OS execution boundary. Cached
references still incur bounded extension traversal; this is no claim that every
upstream parser or semantic operation has a global CPU budget.

The package-data list now includes exactly the unchanged canonical
`english_extension.schema.json`. The regression builds a wheel offline using
existing setuptools/wheel, unpacks it into a disposable private directory and
imports from that directory in an isolated Python process outside the checkout.
It verifies the resource's SHA-256 against the canonical source schema and checks
its schema identity/validity. No dependency installation, native-caller
installation, real-input acceptance or activation follows from packaging proof.
The native parser/transform/cache qualification precondition above remains.
