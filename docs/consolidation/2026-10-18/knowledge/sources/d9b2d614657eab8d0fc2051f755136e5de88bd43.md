## Implemented behavior

The existing Netlify Identity SDK owns provider authorization, token verification, email confirmation, invitations, recovery and logout. Google is rendered only when Identity settings enable it. No Google app, client secret, health scope, credential, role grant or production setting was created.

`public/identity-flow.js` records a token-free, same-tab sign-in intent for 15 minutes. OAuth callbacks require that intent, consume it once, and reject expired or malformed fragments, duplicate or mixed credential types and an inconsistent provider. The marker records local user intent; **Netlify's server-side OAuth state validation remains the security authority**. It does not cryptographically bind a Google response. A callback opened in another tab must restart sign-in there. Confirmation, recovery, invite and email-change links retain the SDK's respective handling and do not require an OAuth intent.

The SDK's successful `AuthError: Redirecting to OAuth provider` signal retains intent while the real browser schedules navigation. Callback processing always removes credential fragments, including failed/cancelled callbacks. The return page uses a fixed OffMenu destination and the same structural callback policy; query parameters cannot choose a return host. Arbitrary provider error descriptions are not displayed.

Cloud saves/restores, shared-kitchen requests, integration grants and consent now use the app's account-bound fetch guard. It checks account identity around refresh, dispatch, response headers and asynchronous JSON/body reads. Cloud restore checks identity again after loading shipped recipes. SDK account events reset private views when another tab signs in or out. User-initiated account actions suppress duplicate SDK event handling and invalidate outstanding requests. Refresh/profile events refresh local user metadata; backend authorization remains fresh and authoritative.

## Linking, roles and privacy contracts

Private data is keyed by the **verified Netlify account ID**, never Google display name, email or browser-supplied ID. If Netlify resolves Google and email credentials to the same ID, the same private cloud kitchen is restored. Equal emails with different verified IDs remain separate. OffMenu does not perform a client-side account merge or provider reassignment. A real existing-account linking flow still needs provider acceptance evidence; the synthetic stable-ID scenario is not proof of live linking.

Google sign-in, a personal kitchen's owner role, provider-dashboard access and user-editable metadata cannot grant application administrator rights. The existing backend uses fresh trusted `app_metadata.roles`; no role/schema changes were made. Roles assigned elsewhere take effect in SDK claims on the next login or token refresh, while application backend checks continue to consult Identity. Guest, demo and signed-in storage stay distinct. Failed cloud restoration does not turn a successful login into a failed login, and local drafts remain in their owner-specific storage.
