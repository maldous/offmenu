## Consumer API

```js
createSessionStateProtocol({
  store,                 // atomic synchronous transaction(work) adapter
  authenticate,          // actual fresh verifiedUser(request), returns {id}
  readSession,           // synchronous reviewed protected credential parser
  authorizeRequest,     // strict true only: method/path/Origin/CSRF policy
  authorizeEnrollment,  // strict true only: explicit server enrollment policy
  audience,             // fixed configured canonical https://<app>/api/state
  realm,                // independent deployment/restore incarnation, 16..128 chars
  ttlMs,                // explicit server policy, 1..86400000 ms
  now                    // trusted finite safe-integer server clock
})
```

There are no permissive default auth, request or enrollment hooks. Every action authenticates again. Provider rejection fails closed; request policy failure cannot touch storage. The operator must apply rate/resource bounds to enrollment and operation retention before deployment. A user-supplied `accountId`, grant ID, expiry or state revision cannot mint authority.

- `enroll(request)` issues random 256-bit session ID and independent capability, stores only its SHA-256 digest plus authenticated subject, realm, epoch 1, fixed resource/scope and server expiry. Returns credentials **only to the server caller** for approved protected transport. No automatic enrollment after missing/revoked state. No localStorage credential transport is implemented.
- `readSession(request)` must return `{sessionId, capability, realm, epoch}` from the reviewed credential transport. All values are untrusted selectors until they match persisted subject, secret digest, realm, epoch, audience, `state:read-write` scope, live status and expiry. Reject duplicate/ambiguous transport credentials in the caller. Production cookie/method/CSRF handling is not supplied by this module.
- `read(request)` returns `{revision,state,binding}` for the authenticated subject only.
- `mutate(request,{operationId,expectedVersion,state})` accepts exactly those three command fields. Operation IDs are 16..128 ASCII alphanumeric/underscore/hyphen; expected version is a nonnegative safe integer with room to increment. Other authority fields are rejected. State must already match the selected validator's canonical output and remain within 2,000,000 bytes. The outer request parser still needs byte/depth/duplicate-key limits.
- A committed result is `{status:'committed', acknowledged:true, operationId, revision:expectedVersion+1, digest, binding}`. `binding` is `{subject,sessionId,realm,epoch,resource}` and contains no capability. `digest` is SHA-256 of sorted canonical JSON for `{audience,method:'PUT',version:expectedVersion,state:<validated snapshot>}`. It is payload integrity/idempotency metadata, not issuer authority.
- A current-version mismatch records `{status:'conflict',acknowledged:false,operationId,revision:<current>,digest,binding}` without changing state. Exact retries return the same terminal outcome, even if other operations later change the current revision. Reusing that operation ID with a different normalized payload/version is `OPERATION_ID_REUSED` (409); conflict retries require reconciliation and a new ID.
- `status(request,operationId)` returns that session's persisted outcome or `{status:'unknown',acknowledged:false,operationId,binding}`. Missing means unknown, never not-executed. Another account/session cannot disclose it. Revoked/expired credentials cannot fetch cached results. Any later same-subject recovery across new sessions needs a separately reviewed status-only policy; it is not implemented here.
- `revoke(request)` durably tombstones this session, remembers the original epoch and increments once. Repeating the same authenticated capability returns the same revoked outcome. Enrollment after explicit later login issues a new session ID, never revives the old one.

Same-subject upstream refresh or token rotation does not rotate an app epoch. A different subject cannot use the old app capability. Logout revokes this app session, including tabs sharing that credential, while independent sessions/devices remain active. Global invalidation is not silently introduced. A still-valid compromised provider credential may enroll another app session under the enrollment policy: app revocation is not provider revocation.

## Storage and race guarantees actually implemented

`createSqliteStateStore(DatabaseSync-compatible database)` uses parameterized statements inside `BEGIN IMMEDIATE`/`COMMIT`. It reads the persisted app row, checks admission, checks the account's state revision, changes `user_state`, and inserts the immutable operation outcome in one transaction. Ledger failure rolls back the state write. Revocation uses the same transaction domain. Callback promises are rejected; transaction bodies cannot await another store/service.

`SESSION_STATE_DDL` exports proposed SQL for **two new owner-prefixed tables**; it is never run automatically. Tests execute it only in private temporary/in-memory databases alongside the existing `cloud/schema.sql`. No production schema file is modified or deployed. Existing `user_state(user_id,revision,state_json,updated_at)` is the only application state interface used.

This adapter is actual synchronous SQLite, **not a D1 adapter**. D1's asynchronous API cannot be substituted for the synchronous transaction interface. Worker 02 must independently implement/qualify equivalent primary atomic conditional SQL/storage ordering; copying the DDL into a migration or wrapping separate async calls is insufficient.

Local revoke-first denies a mutation whose provider check was already in flight but which has not entered the storage transaction. Local commit-first preserves the mutation and its ledger outcome; later revocation neither deletes nor compensates it. A lost commit acknowledgment is returned as `STORAGE_UNAVAILABLE` (503), `outcome:'unknown'`; retrying the same operation under valid authorization resolves the existing outcome without a second write. The same unknown rule covers storage failures where the caller cannot establish commit status.

Provider acceptance remains a point-in-time check before local storage admission. There is no distributed transaction with provider revocation. Storage backup restoration can resurrect old grants/ledgers unless a separately durable deployment/restore realm is rotated before serving writes. Missing tables/rows, invalid stored expiry, unknown scope, changed realm and clock/storage failures never create fallback authority. Do not garbage-collect session tombstones or operation outcomes before the approved retry horizon, or roll back to a bypassing handler. No retention/restore operator is implemented here.
