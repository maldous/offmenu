# Better Auth foundation

This is the first bounded slice of [requirement 32](https://github.com/maldous/offmenu/issues/32), based on reviewed commit `ac04ab98914658bc0443189b3fa04f86ebbc6525`. It adds an **unmounted** Better Auth 1.7.10 factory, explicit additive D1 schema, trusted principal adapter, and synthetic tests. Existing authentication remains in place. No account import, provider registration, credential provisioning, remote migration, or deployment is performed by these files.

## Files and contracts

- `apps/web/server/auth.mjs`: `createOffMenuAuth(env, options)` accepts the native `env.DB` binding, an explicit HTTPS origin in `BETTER_AUTH_URL`, and a separately provisioned `BETTER_AUTH_SECRET`. It requires an explicit `sessionPolicy: {expiresIn, updateAge}` in seconds. Production values must follow verified session requirements; the test's one-hour policy is only a fixture. The factory does not read a request host, generate secrets, run migrations, or mount routes.
- Email authentication is disabled by default. Enabling it requires explicit `email: {enabled: true, allowSignUp, sendVerificationEmail, sendResetPassword}` configuration. The callbacks must deliver through the separately approved sender. Google is absent from `socialProviders`. Synthetic callbacks are confined to the test fixture.
- The factory sets fixed `/api/auth` routing, host-only Secure/HttpOnly/SameSite=Lax cookies, database-backed rate limiting, disabled cookie caching, verified-email requirements, reset-session revocation, and disabled account linking. No role can be supplied through signup/profile input. No administrative plugin or parallel permission system is introduced.
- `apps/web/server/auth-schema.sql` contains only five prefixed tables and three indexes. It was generated against the pinned configuration and checked using Better Auth's migration inspector on native D1. It is safe to apply repeatedly to the initial schema, but is **not** an upgrade engine: future library/schema changes require a separately reviewed migration. `CREATE IF NOT EXISTS` does not repair incompatible existing columns. No request runs this file automatically.
- `apps/web/server/auth-principal.mjs` translates a server-verified session to `{id, name, email, emailVerified, app_metadata: {roles}}`. It preserves the exact opaque ID and omits session secrets and untrusted metadata. Imported role JSON must come from a trusted server source. Malformed role storage denies roles. The adapter requires the session owner to match the verified user and propagates operational failures rather than treating an outage as logout.
- Route checks use `disableCookieCache: true` and `disableRefresh: true`. Session renewal must use the ordinary client session endpoint so its Set-Cookie headers reach the browser. The adapter itself does not renew cookies, accept legacy bearer tokens, or fall back between identity systems.

## Local verification

Run `npm ci --ignore-scripts` and `npm run test:auth` with a Node version supported by the locked Miniflare (tested with Node 24.19.0). These tests use esbuild 0.25.12, Miniflare 4.20260730.0 and workerd 1.20260730.1, matching the inspected lock. All pre-existing package versions are unchanged; Better Auth and its resolved dependencies are additive.

The nine tests include native D1/workerd execution, explicit/repeatable schema application, schema compatibility inspection, no default provider activation, required email verification, secure host-only cookies, trusted-role injection resistance, fresh role removal, rejected wrong-origin writes, tampered/expired/revoked sessions, one-use reset tokens, and reset-response account enumeration resistance. The fixture disables outbound Worker network access and never sends real email.

An imported synthetic user retains its original opaque ID, private state/revision, and AES-GCM owner/source binding. The encryption assertion exercises the current `user.id + '|' + source.id` contract; it does not read a real vault or prove an actual user import. Copying a synthetic password hash between fixture rows is not a Netlify password migration strategy.

The Worker fixture uses `conditions: ['workerd']` and `external: ['node:*']`. It asserts that the native async-hooks export is selected rather than the browser-only fallback and that its synthetic bound secret is not embedded in the compiled script. Missing-schema, bad-origin and missing-provider tests deliberately produce library error logs. Existing application regression tests and the full application build must still run after integration into the current reviewed branch.

## Integration order and ownership

1. Apply these eight files on the latest integration branch. Reconcile `package.json` and `package-lock.json` with concurrent dependency work, preserving other owners' changes. Keep `@netlify/identity` until the later transition is complete. Run the focused tests, full existing tests, and full build. Do not use a historical application snapshot to replace active files.
2. For the later runtime integration, change only the Worker esbuild call to include `conditions: ['workerd']` and `external: ['node:*']`; retain normal browser settings for frontend bundles. Verify the real deployment's `nodejs_compat` configuration. The fixture verifies compatibility date `2026-08-06`; it is not a production settings receipt.
3. Before any live schema/import action, obtain the approved backup/restore and account inventory. Reconcile original IDs, confirmed status, trusted roles, disabled users, duplicate emails and verified provider subject mappings. Preserve existing domain rows, ciphertext, revisions, memberships and audit ownership. Do not infer identity equivalence from matching emails. Resolve password and pending invite/recovery continuity before cutover.
4. Apply the reviewed additive migration explicitly through the approved deployment process. Import each existing user with the original Netlify ID as `auth_user.id`. The existing provider-vault key and ciphertext remain unchanged. New Better Auth sessions are created by the library; Netlify access tokens are not imported as sessions. Provider registrations and persistent credential setup require their separate authorization.
5. Reserve and coordinate `apps/web/server/handler.mjs`, `scripts/build.mjs`, the client/session files, `apps/web/server/locale.mjs`, `apps/web/server/service-support.mjs`, and delegated-admin proof code with their owners. Mount `/api/auth/*` before catch-alls and return Better Auth's response without collapsing Set-Cookie headers. Preserve existing security/no-store behavior. Use the principal adapter through the existing authenticated-handler dependency. Adapt verified-email checks explicitly; do not synthesize legacy confirmation timestamps.
6. Preserve lifecycle guards for account switches, delayed response bodies, failed logout, guest/demo work and restore conflicts. Migrate the administrator delegation proof deliberately: it currently depends on a sealed Netlify JWT. Keep ordinary OAuth/MCP grants, scopes, resource binding and kitchen roles unchanged. No shared dispatcher, data handler, frontend, build or delegated-access file is modified by this slice.
7. Qualify real Google consent and exact-subject restoration with an approved OffMenu-owned client, authentication email delivery, legacy links, session renewal, two-user isolation and rollback in staging before switching production. Historical Netlify-managed Google credentials and a successful real linking flow are not established by the preserved evidence.

## Rollback boundary

Before activation, reverting these source/dependency changes is sufficient; the factory is unmounted. If additive tables have later been created, leave them intact rather than dropping user data as part of a code rollback. After activation, use the retained application artifact and reviewed auth-mode strategy. Never restore the entire D1 database over subsequent pantry edits. New Better-Auth-only accounts and password changes need a tested continuity path before rollback can be claimed safe. Do not fall back to a different identity system after an invalid new session.
