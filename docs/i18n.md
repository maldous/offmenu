# OffMenu internationalization

Integrated into `main` on 14 October 2026. The implementation was prepared on
`codex/offmenu-i18n` in an isolated worktree; that branch/worktree is retired
after integration.

## Interface and content languages

The interface currently supports English and an **Arabic preview**. The Arabic
catalogue is incomplete; missing messages retain their English source text. The
machine-readable [coverage inventory](i18n-coverage.json) records the remaining
work. This is translation infrastructure, not a claim of a fully translated
Arabic release or translated worldwide recipe corpus.

Interface language is independent of country, measurement units, recipe search
language and food-name display language. The header and profile contain language
selectors. A preference is saved under `offmenu-ui-language-v1`; a `uiLanguage`
URL parameter also supports browsers that refuse storage. Selecting a language
reinitializes dynamic views. Persisted pantry/profile/account data and checkout
drafts retain their existing keys and values; transient forms and catalogue
results are not persisted by this language selector.

`public/i18n.js` supplies source-message keys, plain-text parameter interpolation,
plural forms, locale negotiation and number/date/currency formatters. Plural
entries support all six Arabic categories through `Intl.PluralRules`. Add another
interface language by adding a catalogue, registering it in `CATALOGUES` and
`LANGUAGES` and the shared `SUPPORTED_LOCALES` negotiation list, and supplying
any localized installation manifest. Content-language
selection supports supplied French, Japanese, Russian, Arabic and other BCP 47
text without requiring a corresponding interface-language pack.

Both application HTML pages are marked for localization, including titles,
descriptions, labels, placeholders and accessible names. Dynamically generated UI
messages use the same translation layer. HTML/EPUB document exports declare their
language/direction and annotate generated English fallback fragments. Extension
and sign-in return-page copy have the same localization hooks; the fixed-origin
Identity fragment-forwarding code is unchanged. Publisher licence notices and
machine-readable source identifiers remain original evidence.

## Text and identity boundaries

Translate display labels, not identifiers or stored values. Meal-slot options
have explicit English canonical values even when their labels are Arabic.
Barcodes, units, dates used for calculation, resource IDs and country/currency
codes remain unchanged. User-entered names/notes use plain, direction-aware text
instead of being mistaken for interface-message keys. Translation parameters are
rendered with `textContent`, or escaped in document exports; they are never
interpreted as user-supplied HTML.

Arabic sets `html.lang=ar` and `html.dir=rtl`. Logical alignment/spacing supports
RTL, while numeric/barcode inputs, camera pixels and barcode decoding retain
their original behavior. Source text uses its own language and automatic text
direction. Known untranslated interface fragments declare English for screen
readers. Missing/stale corpus translations are identified separately from source
language; missing translations do not exclude a recipe from the library.

Multilingual search includes original names and supplied translations. Accent
folding only removes marks from Latin letters, preserving Japanese voicing and
significant marks in other scripts. Food matching still uses canonical ingredient
IDs and quantities, not translated display text.

## Common corpus contract integration

The **OffMenu task owns** `corpus/common-data.schema.json`, its accompanying
contract, collection/alignment, resource identities and cultural/source evidence.
This branch does not redefine that representation or merge different recipes.

`public/common-corpus-locale.js` implements a read-only adapter for its
`offmenu-common/1` resource/assertion/relation/citation/translation graph:

- Uses stable text IDs, original language, citations and UTF-8 SHA-256 digests.
- Displays `published-source` and `reviewed` translations only when they match
  the current text digest. Draft, stale, missing or conflicting translations
  retain source text and an explicit fallback reason.
- Resolves resource names, source-record aliases, ordered recipe steps and every
  typed value kind, including fixed RDF/XML expressions and Unicode IRIs.
  Expressions render as plain code (`lang=zxx`) and are not display translations.
  Quantities retain dimensions, unknowns, units and source
  notation; the adapter performs no measurement conversions or recipe merging.
- Keeps source/translation evidence in projections and respects resource and
  citation visibility for the supplied account context. Browser filtering is
  supplementary; the server must still enforce access before delivering graphs.
- Uses an immutable snapshot, rejects duplicate IDs and ambiguous aliases, and
  does not replace privately reviewed recipe edits with a public source variant.

Install its synchronous `resolveField` projection through
`configureCorpusResolver` in `public/content-locale.js`. Legacy name maps and
explicitly supplied translation fields remain readable during migration. This
module is a presentation adapter, not a competing corpus schema.

The existing JSON import control in **Connections → food data** accepts common
graphs up to its existing 2 MB limit for local preview. It disables legacy cloud
save/export controls for that preview: no graph is silently converted into the
older private-record format. A source API may supply `commonGraph` alongside
legacy records to activate the same reader. Account changes clear the active
reader. No new corpus publication endpoint or automatic translation service is
assumed by this implementation.

The first real alignment artifact initially failed the uniqueness check: different
assertion properties shared an ID because identity derivation omitted
`propertyId`. The producer corrected identity derivation. The first packet from
`common-recipes-accepted-20261014/recipe-source-alignment.jsonl.gz` now passes
the reader (33 resources, 105 assertions and 34 relations), as does the real
terminology sample. This qualifies samples, not the entire package. The corpus
owner remains responsible for whole-package validation and publication.

## Maintenance and verification

```bash
npm run i18n:extract
npm run i18n:check
npm test
npm run build
```

`i18n:extract` creates `public/locales/en.json` and `docs/i18n-coverage.json` from
marked HTML, frontend messages/metadata and backend-authored messages that can
reach the UI. The inventory is conservative: it also includes source descriptions
and labels passed through variables. It excludes URL/identifier/SQL literals;
actual corpus text is indexed by the common-data contract instead.

`i18n:check` verifies inventory drift, translation placeholders and required plural
fallbacks. The build runs this check before bundling. For a complete Arabic release,
also run `node scripts/i18n-catalogue.mjs --check --complete-ar`; it intentionally
fails while Arabic entries remain missing.

Offline assets bundle catalogues into the application and service worker. Both
installation manifests are cached. The worker matches cached static assets
independently of language/version query strings and continues to exclude private
API/Identity/OAuth traffic from its shell cache.

Focused tests cover locale negotiation, six Arabic plural categories, formatting,
accessible text, canonical form values, source fallback, Unicode search, personal
text, safe HTML/EPUB output, recipe quantity invariants, digest-bound translations,
private citations, immutable graph snapshots and identity collisions. Browser
verification uses a separate Playwright session and synthetic graph fixtures;
it does not sign into or change production accounts.

## Best-effort product locale integration

`public/locale-negotiation.js` shares supported locale matching and precedence
between the browser and edge. Only supported interface locales are selected;
unsupported or malformed signals are skipped. Source-content language support
remains independent of the interface catalogue.

The browser chooses URL `uiLanguage`, explicit device preference, explicit
locale cookie, saved account hint, browser language preferences, edge request
language hint, Cloudflare country fallback, then English. The server chooses URL,
locale cookie, verified OffMenu profile `uiLanguage`, optional Identity/provider
locale (or cached account-language hint), weighted `Accept-Language`, country
fallback, then English. Header quality weights and `q=0` are recognized; GeoIP
cannot reintroduce explicitly excluded Arabic. If all supported languages are
unavailable, the site still falls back to English.

Manual selection stores the device preference and mirrors it in the same-origin
`offmenu_ui_language` cookie. In the main app it also updates `profile.uiLanguage`
for the existing private-state sync. Shared kitchen projections exclude this
account preference; changes made while in a shared kitchen sync privately after
returning to the private account kitchen. A device override takes precedence over
the account default. Inferred languages do not become explicit device preferences.
Blocked cookies or storage retain the URL preference.

The existing Identity flow supplies optional `locale`, `language` or
`preferred_language` metadata in snake_case or camelCase user metadata. Google
[documents locale as optional](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload).
No name, email domain or time zone is used to infer language. On account resolution
or profile restoration, a language-only `offmenu_account_language` cookie records
the account hint, and a locale change reinitializes the app once. Logout clears
the inferred account hint. Auth failures leave the current fallback usable;
cached HTML account metadata alone cannot resurrect a logged-out preference.

`cloud/locale.mjs` consumes [Cloudflare's request country metadata](https://developers.cloudflare.com/workers/runtime-apis/request/#incomingrequestcfproperties).
Only an explicit list of Arabic-speaking-country codes supplies an Arabic hint
when stronger signals are absent; location does not establish a person's language
or change their account country, measurement units or food identity. The
Cloudflare deployment already provides this resource, so it is the implemented
GeoIP provider. MaxMind is an alternative country source for a future hosting
change, not an added paid service or IP lookup on this path. Client-provided
`X-Locale` or `CF-IPCountry` headers are not trusted as platform metadata.

The two HTML application routes use Cloudflare `HTMLRewriter` to translate marked
copy before delivery, including titles, accessible attributes, installation
manifest, `lang` and `dir`. `Content-Language`, `X-OffMenu-Locale-Source`, `Vary` and
`Cache-Control: private, no-store` describe and isolate the response. HTML dataset
attributes carry only locale/source, excluded locales and country hints. Explicit
preferences avoid an account lookup; authenticated requests use the existing
verified Identity and account-scoped D1 read, with graceful outage fallback.

Run `npm run build && npm run test:locale-edge` to qualify the actual compiled
Worker and HTMLRewriter in Miniflare. Its test compatibility date is pinned to
the available local runtime; it does not change production compatibility settings.
Miniflare's development-only `undici` and `sharp` overrides select patched
versions; `npm audit` reports zero vulnerabilities in this dependency set.
The existing OAuth scopes, login callback and token verification are unchanged.
Live Google sign-in and authenticated production flows have not been exercised
by the local mocks.

## Reviewed corpus package compatibility

The reviewed `common-data-20261014` manifest declares full producer schema,
identity, citation and scope validation. The presentation reader independently
passed **521 packets** across **12 files** verified against the manifest's byte
counts and SHA-256 hashes. Sampling covers first/last packets from
first/middle/last partitions of concepts, recipes, terminology and FoodOn, plus
published-translation packets. The actual English-to-Russian publisher
translation retains its source digest and citation identities; sampled formal
expressions remain verbatim. [The probe evidence](i18n-corpus-compatibility.json)
records the exact manifest digest, file hashes and packet positions. These are
consumer checks, not a second whole-package validation of all 79,534 packets.

The probe did not find a source-published English translation of non-English
source text. Parallel English source names may still be present, and English
source recipes are readable as English. Foreign-only text continues to display
its original language with a missing-translation notice. This package therefore
does not establish full English translation coverage for foreign-language
recipes, or full Arabic corpus translation coverage.

Repeat the bounded, streaming qualification against a local reviewed manifest:

```bash
node scripts/verify-common-corpus-reader.mjs /absolute/path/manifest.json /tmp/reader-evidence.json
```

Publication and the hosted manifest are owned by the corpus task. Qualifying this
local package does not add an automatic corpus download endpoint or bypass the
JSON preview import's existing size limit.

## Published handoff verification

The [serving manifest](https://offmenu-corpus.netlify.app/common-data/manifest.json)
and the [immutable deployment manifest](https://6acea38bcfc2cc066ba1ec8f--offmenu-corpus.netlify.app/common-data/manifest.json)
have the same exact-byte SHA-256:
`a20aca224758eb6ac64ea89d0bb31d33280a2b0d2ec97e46ed6a2ddc71c92867`.
All 170 file byte/hash/packet-count entries match the qualified local package,
and a representative published concept part was fetched and verified.
[Hosted handoff evidence](i18n-hosted-handoff.json) records both hashes, exact URLs
and the scope of this independent serving check.

The embedded `manifestSha256` is a **payload hash**: the publisher serializes the
ordered manifest as compact Python JSON, with default ASCII escaping, excluding
that field before hashing. Both embedded payload hashes verify using this rule;
they differ from the final JSON file's exact-byte hash. Use the recorded exact-byte
hash to pin a fetched manifest. Part-file `sha256` values hash the actual file
bytes. Use each serving manifest file's `url` or `releaseBaseUrl`; the partitioned
files are under `common-data/releases/common-data-20261014/`, not directly beside
the serving manifest.

The data task published the package and pushed its contracts. This branch's
application remains undeployed; this verification does not turn the local preview
reader into an automatic package transport or broaden translation coverage.

The publisher has now supplied checked exact-byte sidecars for the
[serving manifest](https://offmenu-corpus.netlify.app/common-data/manifest.json.sha256)
and [release package manifest](https://offmenu-corpus.netlify.app/common-data/releases/common-data-20261014/manifest.json.sha256).
Both match this branch's recorded exact-byte hashes. The
[checksum algorithm receipt](https://6acea54e7b6d662e6991719f--offmenu-corpus.netlify.app/common-data/manifest-checksums.json)
explicitly distinguishes `byteSha256` from `payloadSha256`; the ordered Python
payload serialization is not RFC 8785 canonical JSON. Data-file and manifest
bytes are unchanged by this checksum-only publication.
