# Bounded interface locale refusal

For the Worker's localized `/` and `/data-workspace.html` responses, explicit
URL, saved device/cookie and existing account profile/provider preferences keep
their established precedence. Locale hints do not grant authentication or roles.
After those preferences, the shared policy uses an acceptable supported request
language, country hint or configured default. An excluded supported locale must
not be selected by those inferred/default paths.

If both supported locales (`en` and `ar`) are excluded by the existing parser,
negotiation returns `{locale:null,source:'not-acceptable'}`. The localized HTML
boundary responds with HTTP 406 and only the language-neutral JSON code
`{"errorCode":"locale_not_acceptable"}`. It serves no excluded HTML language,
sets no `Content-Language` or account cookie, and uses `private, no-store` with
`Vary: Accept-Language, Cookie`. The response does not echo private preferences
or request headers, and no new UI is introduced.

Browser setup checks this refusal before language resolution or DOM translation
and throws an error with the same machine code, rather than converting null to
English. Its normal language-string return value is unchanged. Account-language
reevaluation already requests a reload when the negotiated decision differs;
a refusal therefore obtains the refused server response without choosing an
excluded language. App, data-workspace, extension and return-page entry points
retain their successful setup contract.

Static assets and unknown paths keep their existing response/status behavior and
do not read administrator settings, including with both locales excluded.
Normal defaults, one acceptable supported locale and explicit preference cases
retain their existing successful responses.

This is a conservative application policy for the existing supported locale and
header parser. It does not claim universal HTTP language-range compliance or add
wildcard, malformed-range, additional-language or subtag-exclusion semantics.
Production rollout, credentials, schema and workflow settings are unaffected.
